1. Se connecter au cluster

  • Adresse : propriété spring.kafka.bootstrap-servers = ${KAFKA_BOOTSTRAP:localhost:9092}.
  • Clé : chaîne UTF-8 (StringSerializer) ; valeur : JSON UTF-8 en octets (ByteArraySerializer).
  • Producteur du Core : acks=all, idempotence activée, une requête en vol par connexion (ordre par clé). Les événements d'agrégat passent par l'outbox de yow-event-kernel : publication « au moins une fois ».
  • Topics créés au démarrage (TntKafkaTopicsConfig) : KAFKA_PARTITIONS partitions (3), réplication KAFKA_REPLICATION (1 en local) ; topics d'agrégat en cleanup.policy=delete, rétention TNT_KAFKA_AGGREGATE_RETENTION_MS (30 jours) pour qu'une plateforme externe puisse rattraper son retard.
  • Démarrage d'un nouveau lecteur : auto.offset.reset=earliest lit les 30 derniers jours ; un projecteur doit donc supporter un historique complet (voir bonnes pratiques).

2. Les cinq topics d'agrégat

3. Distinguer les événements d'un même topic

Tous les types d'événements continuent d'être produits et traités ; regrouper les topics n'en supprime aucun. Un consommateur choisit ce qui le concerne ainsi :

  1. eventType (corps) ou l'en-tête X-Yow-Event-Type : le nom exact (DeliveryDelivered, ParcelReturnRequested…). Filtrer sur l'en-tête évite de désérialiser le corps.
  2. aggregateType (PARCEL, DELIVERY, ANNOUNCEMENT, INCIDENT, DISPUTE, en-tête X-Yow-Aggregate-Type) : un seul par topic.
  3. La transition previousState.status → payload.status : un même type peut suffire (ex. ParcelReturnRequested), mais une réaction précise lit la transition et les champs (ex. l'agence expire un colis sur AT_RELAY_HUB → RETURN_REQUESTED avec returnCause = NOT_COLLECTED_AT_RELAY). previousState = null = création.
  4. details : les données propres au type (motif d'échec, alerte, indemnisation…), décrites par un schéma par type (§4).
  5. Un enregistrement sans schemaVersion (ancien format) est ignoré : TntAggregateEvent.isAggregateEvent.

Ordre et doublons : la clé est l'id de l'agrégat (même partition, donc ordre de publication), mais l'outbox peut rejouer un ancien enregistrement. aggregateVersion croît d'une unité par sauvegarde : un projecteur ignore une version ≤ la dernière appliquée. Un effet unique (paiement, ouverture de litige) se protège par eventId (table event_bus.processed_events dans le Core). Règle du Core : une transition par sauvegarde.

// Exemple (Java, Spring Kafka) — ne réagir qu'à la remise au destinataire
@KafkaListener(topics = TntTopics.DELIVERY_EVENTS, groupId = "ma-plateforme-delivery")
void on(ConsumerRecord<String, String> r) throws Exception {
    JsonNode ev = mapper.readTree(r.value());
    if (!TntAggregateEvent.isAggregateEvent(ev) || !"DeliveryDelivered".equals(ev.path("eventType").asText())) return;
    if (ev.path("aggregateVersion").asLong() <= lastApplied(ev.path("aggregateId").asText())) return; // rejeu
    apply(ev.path("payload"));
}

4. Enveloppe, en-têtes et schémas

Champs obligatoires : eventId, eventType, schemaVersion, occurredAt, aggregateType, aggregateId, aggregateVersion, tenantId, trigger, actor (type parmi COURIER, SENDER, RECIPIENT, RELAY_OP, AGENCY, SUPPORT, SYSTEM), previousState, payload, details. Facultatifs : correlationId, causationId. Des champs peuvent être ajoutés sans préavis ; un changement cassant incrémente schemaVersion.

En-têtes : X-Yow-Event-Id, X-Yow-Event-Type, X-Yow-Aggregate-Type, X-Yow-Aggregate-Id, X-Yow-Schema-Version, X-Yow-Tenant-Id, X-Yow-Correlation-Id, X-Yow-Envelope-Id, X-Yow-Solution-Code ; X-Yow-Replay: true seulement sur une relance manuelle (§10). Les en-têtes reprennent le corps à l'identique.

Données personnelles masquées : pas de téléphone ni d'adresse exacte (quartier, ville, pays, coordonnées arrondies à 2 décimales, environ 1,1 km), nom affiché « Prénom N. ». Le détail s'obtient par l'API, avec les droits.

Schémas JSON (draft 2020-12, foundation/tnt-common-core/src/main/resources/kafka/schemas/v1) ; types ayant un schéma de details : AnnouncementResponseReceived, AnnouncementResponseWithdrawn, DeliveryAlertCleared, DeliveryAlertRaised, DeliveryAttemptFailed, DeliveryCancelled, DeliveryEtaUpdated, DeliveryFailed, DisputeAwaitingEvidence, DisputeClosedResolved, DisputeCompensated, DisputeEvidenceAdded, DisputeOpen, DisputePendingArbitration, DisputePendingCompensation, IncidentCancelled, IncidentEscalated, IncidentEscalatedToDispute, IncidentHandlerAssigned, IncidentHandoverConfirmed, IncidentPendingConfirmation, IncidentReported, IncidentResolved, IncidentTriaged, ParcelCustodyChanged, ParcelDamaged, ParcelLost, ParcelReturnDeliveryCancelled, ParcelReturnRequested.

kafka-acls.sh --bootstrap-server $KAFKA --add --allow-principal User:agency \

  --operation Read --operation Describe --group ext-agency- --resource-pattern-type prefixed

La gestion de ces comptes et ACL est un besoin de la plateforme d'administration (spec §5.5).

8. Bonnes pratiques

  • Idempotence par eventId : tout effet unique (paiement, notification, création) doit survivre à un rejeu.
  • Ordre par aggregateVersion : ignorer une version déjà appliquée ou plus ancienne.
  • Ignorer les champs inconnus (FAIL_ON_UNKNOWN_PROPERTIES=false) et les types d'événements inconnus : de nouveaux s'ajoutent sans changer schemaVersion.
  • Filtrer tôt sur l'en-tête X-Yow-Event-Type ; acquitter les événements qui ne concernent pas le lecteur.
  • Dans le Core, attendre la fin du travail réactif dans le listener (ReactiveListenerSupport.await, 30 s au plus) : un échec est retenté 4 fois (1 s, ×2) puis envoyé dans tnt.dlq ; ne jamais avaler une erreur (onErrorResume(e -> Mono.empty())).
  • Ne pas passer de clé explicite à l'outbox : la clé est l'id de l'agrégat.
  • Ne jamais publier de données personnelles en clair ; passer par TntEventMasking.
  • Un topic nouveau = une constante TntTopics + un NewTopic (test KafkaAsyncWiringTest.everyTopicConstantIsDeclared) + une ligne de ce guide.

10. Relancer un message de tnt.dlq

Un listener du Core qui échoue encore après 4 tentatives publie l'enregistrement dans tnt.dlq avec sa clé, sa valeur, ses en-têtes et kafka_dlt-original-topic, -partition, -offset, -original-consumer-group, -exception-fqcn, -exception-message. Journal KAFKA_RECORD_DEAD_LETTERED, compteur yow_event_consumer_dead_lettered_total{topic,group}.

  1. Lire la file avec ses en-têtes : 
    kafka-console-consumer.sh --bootstrap-server $KAFKA --topic tnt.dlq --from-beginning \
  --property print.key=true --property print.headers=true --property print.timestamp=true
  2. Comprendre la cause (kafka_dlt-exception-message), corriger (code, donnée, configuration).
  3. Republier l'enregistrement à l'identique (même clé, même valeur) sur kafka_dlt-original-topic, avec l'en-tête X-Yow-Replay: true : c'est le seul cas où l'anti-doublon event_bus.processed_events laisse repasser un eventId déjà traité. 
    printf '%s\t%s\t%s\n' 'X-Yow-Replay:true' '<clé>' '<valeur JSON sur une ligne>' | \
kafka-console-producer.sh --bootstrap-server $KAFKA --topic <topic d'origine> \
  --property parse.headers=true --property parse.key=true --property key.separator=$'\t'
  4. Noter la relance (qui, quoi, pourquoi) : elle relève du journal d'administration. Une route d'API de relance est à construire (spec d'administration §5.5) ; ce mode opératoire la remplace en attendant.

Attention : relancer un enregistrement dont l'effet a déjà été appliqué en partie peut le réappliquer (une notification peut repartir). Vérifier l'état avant.

11. Exploitation : anciens topics d'un cluster existant

Spring Kafka crée les topics manquants mais n'en supprime aucun. Sur un cluster existant, tout topic tnt.* absent du catalogue (hors tnt.trust.*) est un ancien topic : vider les lecteurs (offsets en fin), vérifier qu'aucune plateforme externe ne le lit, puis kafka-topics.sh --delete --topic <nom>. La liste complète (42 migrés, 22 morts) est dans le journal technique du chantier, lot L8. La rétention de tnt.delivery.events existant avant le lot L0 doit être réglée une fois (kafka-configs.sh --alter --entity-type topics --entity-name tnt.delivery.events --add-config retention.ms=2592000000).
